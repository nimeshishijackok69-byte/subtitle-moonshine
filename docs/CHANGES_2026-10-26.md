Live subtitle pipeline: Silero VAD → SenseVoice ONNX → anchored committer → overlay.

Everything below was changed in the working tree on top of `ec46509`.

## 1. What was broken, and what fixed it

| # | Defect | Root cause | Fix | Evidence |
|---|--------|-----------|-----|----------|
| 1 | VAD never fired. Subtitles only appeared on luck. | Silero v5 was fed bare 512-sample frames. The reference wrapper prepends 64 samples of left context (576 total); without it the encoder collapses to a "no speech" prior and **raises no error**. | Keep a 64-sample rolling context and feed `576` samples per call. | Median speech probability on the same 60 s of dialogue: `0.0005` → `0.8988`. Max `1.0`. 58.6% of frames ≥ 0.5. Music-only cold open stays shut (max `0.085`). |
| 2 | A late `GROW`/`INTERIM` overwrote a line that had already been `FINAL`ised. | The 750 ms tick and the utterance-final flush both called into the same ONNX session; whichever returned last won. | One promise chain per session (`withAsrLock`). ## 2. What the two CSVs actually prove

`black_clover_live_run.csv` (557 rows) and `blade_runner_run.csv` (604 rows), both exported from the live extension.

- **The second file is not a second run.** Its first 557 rows are byte-identical to the Clover export; only the trailing 47 rows are Blade Runner. Telemetry was never reset between sessions. Fixed by `telemetry.reset()` on `CLEAR_ALL`.
- **`E2ELatencyMs` is not latency.** Every value sits between 20 760 and 21 254 ms with no correlation to anything. It was a time-origin offset. This is why the new columns exist.
- **ASR compute was never the problem.** p50 314 ms / 233 ms, p90 444 / 441, max 510. Two thirds of a second worst case.
- **The cadence was.** Audio position advanced by exactly 1.20 s per row, p90 2.40 s. The 2.4 s rows are dropped ticks, i.e. the decode queue was saturating.
- **Output shape.** 8 characters per line median, 15 at p90. 24.1 lines/min over 23.1 minutes.
- **Hallucination residue.** 4.1% exact-duplicate rows; `あ。` six times, `はい。` four times, `こ。` three times.

Reading these together: the extension was not slow, it was **silent and then noisy**. VAD never opened, so nothing was decoded; when it did open, every decode became its own line.

## 3. Why the anchored committer, not a sliding window

A sliding window re-decodes overlapping audio and appends each result. Measured on 305 subtitle lines of *Mushoku Tensei* S3E14 against the ASS dialogue track, that produced 5.18 lines per sentence and **36.6% of committed updates were later contradicted** — the viewer reads a word, then watches it change.

The anchored committer fixes the left edge at the VAD onset minus pre-roll, grows the right edge, and only publishes text that two consecutive decodes agree on, minus a 4-character holdback. Same corpus: **1 line per sentence, 1.7% contradicted**.

The holdback value came from a sweep, not from taste. `HOLD = 4` with one-tick agreement; two-tick agreement measured worse because it published later without publishing more accurately.

Two things were considered and **rejected**:

- **Token timestamps for committing.** SenseVoice is CTC; peak positions are not validated against real audio, so committing on them would have been an unmeasured guess dressed as precision.
- **The model's own `<|Speech|>` / `<|BGM|>` tag as a gate.** On the benchmark it classified 67.2% correctly versus 55.1% for the existing path — not enough margin to replace a working mechanism.

## 4. Verification

Two harnesses, both driving the **shipped** functions rather than copies. They live in a scratch directory outside the repository (they need the local ONNX model files and an absolute repo path), so they are not part of the commit.

`vmtest.js` loads `offscreen.js` into a VM with the real ONNX session (CPU provider instead of WASM) and calls `runVad`, `tickAnchoredUtterance`, `finishUtterance`, `normalizeTranscript`, `telemetryFor`:

```
VAD dialogue-dense  with context p50=0.8988   no context p50=0.0005
VAD cold open       with context max=0.0848   (stays closed)
committer           GROW monotonic prefixes: true, holdback 4 chars
revision            REVISE rewrote in place (no stall): true
race                FINAL is last: true
normalize           13/13 cases
```

`domtest.js` loads `contentScript.js` against a minimal DOM shim and drives the real message listener:

```
38/38 assertions pass — rows, tail inlining, FINAL collapse, interim-only
utterances, showInterim, sticky dismissal, row-count rebuilds, late-event
rejection after FINAL, latency decomposition, CSV columns, telemetry reset,
legacy messages
```

The FINAL-tail assertion was mutation-checked: against a copy with the old `setRowContent` comparison it fails (`2 CHECK(S) FAILED`), against the shipped file it passes. That is what distinguishes a regression test from a test that happens to pass.

`node --check` passes on all seven JS files.

**Not verified:** anything requiring a real tab-audio session. The share picker, the WASM execution provider, and actual on-screen latency still need one manual run. That is what the new `SoundToSubtitleMs` column is for — start a session, let it run a few minutes, export, and the p50 of that column is the number to judge.

## 5. Deliberately not changed

- **`HOLD = 4` and 750 ms cadence.** Both are measured, and neither is the current bottleneck.
- **Duplicate suppression.** `あ。`/`はい。` repeats are a real annoyance, but suppressing short lines would also delete real interjections. Needs a decision about what counts as evidence, not a threshold guess.
- **The 8 s utterance cap.** It truncates long sentences, but removing it costs final-decode latency on exactly the utterances that are hardest to read.
- **`context.md`, `implementation_plan.md`.** Historical, and the README says so.

---

## 6. Known issues that remain

1. **Committed text is stable, not correct.** A misrecognition that survives agreement and holdback stays on screen until the utterance ends. The old pipeline corrected itself by rewriting everything; this one trades that for readability.
2. **The first committed text still lands around 2 s into an utterance** — one decode interval plus one agreement tick. Lowering the cadence would help; the ASR budget (p50 ~240 ms) allows ~500 ms, but that doubles decode count and needs its own measurement.
3. **`AudioLagMs` will be non-zero and is currently unmeasured in the wild.** If it is large, the bottleneck is upstream of ASR (worklet buffering or the tab-audio tap), not the model.
4. **No automated end-to-end test.** Everything above is unit-level.
