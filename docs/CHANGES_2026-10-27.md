# Change log — 2026-10-27

Audit of the second-pass changes on top of `3a964f2`, and the fixes applied.

The work under review came from an outside reviewer that edited code instead of
only reporting. Each claim was re-checked against the shipped code and, where
possible, against the real model. Verdicts: **confirmed**, **confirmed but
overstated**, or **wrong**.

Three real defects were found in that change set: one visible bug in the
committer, one total-failure regression in the audio worklet, and one design gap
in the offscreen teardown. All three are fixed below except the teardown
durability, which is documented.

---

## 1. Claims that hold

| # | Claim | Verdict | Evidence |
|---|-------|---------|----------|
| 1 | A 1.0 s decode window silently dropped sub-0.5 s speech | Confirmed | `finishUtterance` returned before decoding whenever `end - anchorStart < MIN`. On `benchmark_16k.wav` the three cited bursts decode correctly once the window is widened: `やらない。`, `ただ?`, `それから?` (88/52/53 ms). |
| 2 | The 1-pole 7.2 kHz filter was too shallow for 48→16 kHz | Confirmed | Computed response: 1-pole is −8.79 dB at 16 kHz, the shipped 4th-order Butterworth is −40.85 dB, a 32.1 dB improvement. Gemini's −42.5 dB figure is within rounding of the bilinear-warped design. |
| 3 | The worklet computed an `rms` nobody read, and copied samples through `DataView` | Confirmed | `grep` finds no `rms` consumer in any file. The `DataView` loop was 640 `setInt16` calls per chunk. |
| 4 | `computeFeatures` allocated a `Float64Array` per frame | Confirmed | 800 allocations per 8 s decode. `power` is fully consumed inside the same frame iteration, so hoisting it to the constructor is safe. |
| 5 | Every progressive tick sent two messages and painted twice | Confirmed | `GROW`/`REVISE` cleared the tail, then a separate `INTERIM` restored it. Emission count on the 8-tick trace: 8 `INTERIM` before, 5 `GROW` + 3 `INTERIM` after. |
| 6 | Re-compiling the 239 MB model on every stop is a 3–6 s cost | Confirmed in principle | `disposeSessionResources` never releases `asrSession`, so a warm offscreen document really does skip `loadAsr`. |

Two claims are weaker than stated:

- **"Eliminating inharmonic alias foldback."** At the 8 kHz Nyquist point the new
  filter is only −4.6 dB. The 8–10 kHz band still folds into 6–8 kHz at −4.6 to
  −12.8 dB. The improvement is real but concentrated above 10 kHz.
- **"SenseVoice decodes every short utterance accurately."** It decodes the three
  benchmark bursts correctly at a 1.0 s window. At 2.0 s the window reaches into
  the previous line and the output absorbs it (`だと思います、ただ。`), so the
  accuracy is a property of the 1.0 s bound, not of short audio in general.

## 2. The committer bug (BLOCK, fixed)

`tickAnchoredUtterance` computed the inline tail **before** updating the committed
prefix, then reused it for the `GROW`/`REVISE` message:

```js
const interimTail = text.slice(u.committed.length).trim();  // old prefix
if (upTo > u.committed.length) {
  u.committed = text.slice(0, upTo);                        // new prefix
  ... text: u.committed, tail: interimTail                  // tail starts too early
}
```

Every committed update therefore re-rendered the characters it had just committed:

| Decode | Committed | Tail | Rendered |
|--------|-----------|------|----------|
| `その時はちゃんと` | `その時は` | `その時はちゃんと` | `その時はその時はちゃんと` |
| `あいそうだねえ` | `あ` | `あいそうだねえ` | `ああいそうだねえ` |

The `REVISE` path failed the other way: the tail started after the *old*, longer
prefix, so the characters a revision removed disappeared from the row entirely
(`あそうだねえ`, missing `い`).

It is invisible in the DOM harness because that harness sends `tail` directly and
never runs the offscreen committer. It is also invisible at rest, because `FINAL`
rewrites the row with the full decode — the doubled text only shows during the
750 ms between ticks, which reads as flicker.

**Fix:** decide the next committed prefix first, then derive the tail from it.
`GROW` and `REVISE` share one emission path; `INTERIM` keeps the tail-only shape.
The tail is no longer `.trim()`ed, so a commit boundary that lands on a space
still reconstructs the decode exactly.

## 3. The anti-aliasing filter was unstable below 15 kHz (BLOCK, fixed)

`fc` was hard-coded to 7500 Hz and never checked against Nyquist. For
`sampleRate < 15000`, `sin(w0) < 0` makes `alpha` negative, `a0 < 1`, and
`a2 > 1`, so both biquad poles sit outside the unit circle. The state then runs
to `Infinity`, then `NaN`.

The failure is silent. `Math.max(-1, Math.min(1, NaN))` is `NaN`, `NaN < 0` is
false, so `NaN * 0x7fff` stores `0` in the chunk. After ~240 ms the worklet
streams digital silence for the rest of the session: VAD never fires, no
subtitles appear, and nothing raises an error. The 1-pole RC this replaced was
stable at every rate, so this was a regression.

Measured on the shipped processor at a constant 0.5 input:

| Context rate | Before the guard | After the guard |
|---|---|---|
| 48 kHz | stable | stable |
| 44.1 kHz | stable | stable |
| 22.05 kHz | stable | stable |
| 16 kHz | stable, but a no-op | bypassed |
| 14 kHz | NaN at 240 ms, tail silent | bypassed, stable |
| 12 kHz | NaN at 240 ms, tail silent | bypassed, stable |
| 8 kHz | NaN at 240 ms, tail silent | bypassed, stable |

Reachable through any default output device below 15 kHz — BT HFP/HSP telephony,
some USB handsets, virtual cables, a user-set 8 kHz default.

**Fix:** design the filter only when the source rate is above the 16 kHz target,
and clamp `fc` to `min(7500, 0.45 * sampleRate)` so the design stays below
Nyquist at every rate. Below the target there is nothing to alias, so the filter
is bypassed and the resampler upsamples instead.

## 4. Backward expansion could reach the previous line (fixed)

`finishUtterance` widens a short window backwards by up to 0.3 s past the
pre-roll. If two utterances are closer than that, the window contains the tail of
the previous one. Demonstrated on the benchmark: the same `ただ。` segment decodes
as `だと思います、ただ。` at a 2.0 s window, and the measured overlap at the real
minimum gap is up to ~154 ms of the previous line's last syllable. Because
`FINAL` owns the line, whatever gets absorbed is printed twice.

**Fix:** the session now records `lastFlushEnd` (the end of the previous decode
window, including tail pad). The widened start is clamped to it; any remaining
shortfall is covered by the existing left-pad. The stream-start path already
proves a silence-padded 1.0 s window decodes these bursts correctly, so this
costs no accuracy.

## 5. The keep-warm timer is not durable (hardened, durability unchanged)

`service_worker.js` schedules offscreen teardown with a 5-minute `setTimeout`.
An MV3 service worker is terminated after ~30 s of inactivity, and a pending
timer does not count as activity, so the timer dies with the worker. The offscreen
document is not closed when the worker dies.

Net effect: the warm restart works; the cleanup usually does not. The first
session can pin the 239 MB model in memory until the extension is reloaded or the
browser exits.

Applied here: the timer callback is wrapped in `try/finally` so a rejected
`closeDocument()` cannot leave an unhandled rejection or a stale handle, and the
README no longer claims the document is closed on `idle`.

Not changed: `chrome.alarms` is the durable mechanism (minimum 1 minute) but
needs `"alarms"` added to `manifest.json`. That is a permission change and a
teardown-policy decision, so it is left as a follow-up.

## 6. Smaller notes

- `MIN_UTTERANCE_SAMPLES`'s comment claimed short bursts were dropped. That is no
  longer true; the comment now describes the widened window.
- The `oldest` bound in `finishUtterance` duplicated `ring.read`'s own clamp and
  read `ring.writePos` directly. Removed; `read()` already clamps, and the
  stream-start padding covers the remainder.
- `flushChunk`'s `new Int16Array(this.pendingBuffer)` is a copy, not a view, so
  transferring its buffer does not detach `pendingBuffer`. Correct as written.
- No consumer ever read `rms`, so dropping it from `PCM_CHUNK` is safe.
- The one remaining early return in `finishUtterance` (`pcm` empty) would leave
  the last `GROW` on screen. It is unreachable today because an utterance cannot
  exist without appended audio, but it is the exact state the comment below it
  warns about.
- `processBiquad` runs the higher-Q section first. The cascade is commutative in
  float64, so this only matters for a fixed-point port.
